01 / 问题

真正贵的，是代码之外的串联

每个环节 AI 都能参与一点。但能力散落在不同对话、工具和命令里，最后负责串起来的还是人——反复梳理上下文、切换平台、判断下一步、回忆哪些经验要留下。

之前 · 人肉串联

  • 需求文档、历史口径、代码事实分散在各处，每次重新讲背景
  • 需求平台 / CR / 配置 / 日志 / 监控手动来回切，上下文一路丢
  • 澄清和 CR 的反馈留在聊天框，需求结束就蒸发
  • 验收靠「人肉点一下看看」，没有可回读的证据
  • 下个类似需求，同样的解释再来一遍

之后 · Agent 闭环

  • 按阶段拉取上下文快照，事实不全就回退补齐，不让 Agent 猜
  • 平台能力变成可调用的工具槽位，Agent 按阶段串起来
  • 反馈落在 CR 评论与 decision-log，结项时蒸馏成长期知识
  • 独立环境里用日志 / 指标 / 调用返回取证，写进 verification
  • 每做一个需求，Agent 的理解基线更高，人要解释的更少
02 / 静态架构

四层能力，一条闭环

不是并列模块，而是从事实输入、阶段判断、工具落地到反馈回收的一条链。反馈学习层把稳定知识蒸馏回长期 wiki，下一次需求的起点就更高。

LAYER 01

上下文输入层

按阶段拉取长期业务知识、当前需求材料、代码事实与运行证据，而不是一次性塞满 prompt。

Agent 靠什么理解业务？
LAYER 02

业务专家编排层

阶段判断、门禁判定、回退与人工介入决策全部可复现，不再靠人盯着下一步。

下一步该做什么？
LAYER 03

工具执行层

需求平台、代码与 CR、配置、日志监控、文档变成按阶段可调用的能力槽位。

具体动作怎么落地？
LAYER 04

反馈学习层

评论、验收证据与人工修正持续积累，结项时选择性蒸馏成知识与 skill 改进。

下次能不能更好？
03 / 纵向闭环

一个需求怎么走完

点选任意阶段查看它的输入、产物与停止条件。G1 / G2 由人在 CR 上确认，G3 由 git hook 自动执行，发布动作始终由人完成。

04 / 质量门禁

三道质量门 + 一道人工审批

门禁不是「提醒 Agent 注意」，而是「不满足就不能往下走」。G3 尤其不靠提示词自觉——它是一条绕不过去的 git hook。

G1 · QUALITY

需求澄清门

  • 目标行为与非目标边界已写明
  • 验收标准可验证且有证据形式
  • 风险与待确认问题已列出
人把关 · 在 CR 上确认 requirements
G2 · QUALITY

技术方案门

  • 现状 / 改动点 / 风险 / 回滚齐备
  • 验收方式在方案阶段就定死
  • 配置 schema 已创建并校验
人把关 · 在 CR 上确认 plan
G3 · QUALITY

内部质量门

  • diff-to-test：每处改动都有测试锚点
  • lint / PMD 与全量单测通过
  • Agent 对完整 diff 做结构化 review
git pre-push hook · 无人值守，不做就推不上去
G4 · APPROVAL

发布确认

  • 独立环境验收通过并留有证据
  • 变更材料、风险评估、回滚预案齐备
  • 观察期继续回读日志与指标
人确认并执行 · Agent 不自动发布
05 / 接入

三步就能跑起来

CLI 零运行时依赖，不调用任何外部平台；skill 是框架无关的 Markdown，可以塞进任何 Agent 体系。

01

装质量门

reqflow hooks install 把 G3 绑到 git push，立刻获得 diff-to-test + lint + test 硬卡口。

02

初始化需求

reqflow init <name> 生成上下文快照、requirements、plan 等 7 份产物模板与状态文件。

03

按阶段推进

reqflow status / advance / gate 让每步决策落到 decision-log，结项时直接拿来做蒸馏。

terminal — install
# 零依赖，clone 即可自检
$ git clone https://github.com/webxiongda/reqflow.git && cd reqflow
$ node bin/reqflow.mjs validate
✓ workflow 校验通过：4 层 / 8 阶段 / 4 门禁（3 质量门） / 7 产物
$ node bin/reqflow.mjs init my-feature --hooks
✓ 已生成需求工作区 / 已安装 pre-push hook
